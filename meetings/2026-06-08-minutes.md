Dan: how should package developers use attestation to protect aganst attacks such as typosquatting?

Andrew: Tooling has been [delayed] a long time... Now that supply chain attacks are more common there is more action. For NPM - which is maybe 95% - for the longest time the defaults have been bad. Produced lots of potential problems. Optimized for UX but often drops security on the floor. So it can be easily attacked and therefore is being attacked a lot.

... so in the guidelines for libraries - there are going to be some specific things there that would make sense only for the publishers. Mainly that they should be using trusted publishing. That comes with caveats because trusted publishing only works with a few hosts. But most people will be using GitHub. It's a signifigant improvement though. Storing a long-lived key in github env that is exposed often.. can be re-used to publish malicious versions of libraries with no paper trail. Because of how NPM's defaults work, that [has bad consequences]. 

... so a number of differnt ways - different configurations - a link to my blog post on "cool down". If you're going to do that you should have a dependabot or renovate ... both of those services... will be good. Also should look at the transitive dependencies. Dependabot can be configured with a cool-down. When you run npm install locally you want the saem cool-down config. You should also probably disable the scripts. There's a flag `--ignore-scripts` - but probably should config local NPM to disable scripts. Also PNPM disabled it for everything... except a few popular known packages. A recent addition in NPM is "staged publishing" - puts a 2fa gate in the trusted publishing process. So you need a hardware key for those to go through. It means noone else can publish unless they have the 2fa hardware key. NPM has this but it's fairly new.
